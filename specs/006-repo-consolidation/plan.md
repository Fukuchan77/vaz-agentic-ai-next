# 006-repo-consolidation — 設計書

`spec.md` に準拠。散文は日本語、識別子・型・パス・コードは英語。

## 1. 設計の骨子

統合の実質は **3 つの操作**に分解される。統合計画はこれを Phase 0〜5 の時系列で述べているが、
本設計は**依存の向き**で整理する。

```
[A] 同一性の移行        退避 → 名前空け → rename → リテラル更新
       │                （R1 → R2）不可逆操作を含む。最優先かつ単独で着地させる
       ↓
[B] 仕様層の受け入れ    正本レビュー設置 → 憲章 → 継承 spec → ADR-0003
       │                （R3 → R4）コード移動ゼロ。[A] 完了で 7 参照が自動解決
       ↓
[C] 実装層の受け入れ    ガイド背骨 → services/api → patterns → ギャップ充填
                        （R5 → R6 → R7 → R8）ここで初めてコードが動く
```

**[A] と [B] の間に他の作業を挟まない。** [A] は GitHub 側の状態を変える操作を含み、
中断すると「名前は空いたが rename していない」という復旧しにくい中間状態が残る。

## 2. 主要な設計判断

### 2.1 ADR-0003（新規）— 統合の向きと組み立て機構

| 論点 | 継承 spec `001-agentic-ai-core-p0` | 本 spec | 採用 |
|---|---|---|---|
| 統合の向き | 新リポジトリ ← `vaz-ai-next` を T-0 で**取り込む** | `vaz-ai-next` を**リネームして昇格** | 本 spec |
| ルート `pyproject.toml` | T-1.3 で新設（`[tool.turbo] name` 必須） | **作らない** | 本 spec |
| `turbo.json` | T-1.2 で新設 | **作らない** | 本 spec |
| Python レーンの配置 | `apps/agent-api` | **`services/api`** | 本 spec |
| uv workspace メンバー | ADR-P0-05 候補 (a): **含めない**・独自 lock・mise 直接実行 | 同左（ルート自体を作らない） | **両者一致** |

**最終行が重要**: 両文書は独立に同じ結論へ到達している。継承 spec は turbo の Python サポートを
有効化しようとしたうえで「退避経路（ADR-P0-01）」へ降り、`apps/agent-api` を uv workspace から
外した。統合計画は最初からルート workspace を作らない。**本 spec は後者を採るが、その根拠は
継承 spec の ADR-P0-05 の論証をそのまま再利用できる**（二層バージョン方針と単一 lock の構造的非両立）。

ゆえに ADR-0003 は「継承 spec を否定する ADR」ではなく、**「同じ結論の極限形を採り、
そこへ至る機構だけを差し替える ADR」**として書く。supersede 対象は 4 タスク
（T-0 / T-1.2 / T-1.3 / T-2）に限定し、53 要件は温存する。

### 2.2 なぜ「削除」ではなく「archive リネーム」を既定にするか

ユーザ指示は削除だが、その指示は統合計画の「空リポジトリ」記述に基づく。実測では非 main
6 ブランチに約 5,400 行の資産がある（`spec.md` 前提誤り 1）。

目的（`vaz-agentic-ai-next` という名前を空ける）に対する 2 手段の比較:

| 手段 | 名前が空くか | 可逆性 | ブランチ資産 | 失敗時の復旧 |
|---|---|---|---|---|
| `-archive` へリネーム | **空く** | **可逆**（再リネームで戻る） | **全保全** | 容易 |
| 削除 | 空く | **不可逆** | 退避漏れがあれば消失 | 不能 |

名前空けという目的において両者は**等価**であり、リスクのみが異なる。ゆえに既定は archive。
削除は R1.3 の 9 ファイル行数検証が green で、かつユーザが明示的に選んだ場合の**選択肢**として残す
（R2.2）。これは指示の拒否ではなく、前提が崩れたことの報告と、目的を満たす代替の提示である。

### 2.3 正本レビューの「同一性崩壊」をどう扱うか

正本レビューは §1 の横断マトリクスで `vaz-ai-next` と `vaz-agentic-ai-next` を**別の列**として扱い、
§5 でそれぞれ別の取り込み主軸を与えている。統合後、この 2 列は 1 本のリポジトリを指す。
本文をそのまま置くと自己矛盾して読める。

3 案の比較:

| 案 | 内容 | 判定 |
|---|---|---|
| (a) 本文を書き換えて 1 列に統合 | 読みやすい | **却下**。追記のみ規約に反し、2026-09-06 時点の測定記録が失われる |
| (b) 設置しない | 矛盾は生じない | **却下**。7 参照が dangling のまま。統合計画の Phase 0 が未達 |
| (c) **verbatim ＋ §6 addendum** | 本文は点時記録として保全、崩壊は写像表で明示 | **採用** |

(c) は `pydantic-ai-agentic-patterns/CLAUDE.md`（「レビュー文書は追記のみ」）と
ハブ既存 spec の運用（003/004 の日付付き addendum）の両方に一致する。

### 2.4 model-ID ゲートの精密化（R6.4 案 c）

現在のハブのゲートは substring grep:

```
PATTERN='claude-[a-z0-9]|llama-?[0-9]|gpt-[0-9]|gemini-[0-9]|qwen[0-9]|mistral-[a-z0-9]'
scan: apps/** packages/** services/**  (--include *.ts *.tsx *.py)
carve-out: packages/config/** , packages/schemas/src/env.ts , services/agent/app/config.py ,
           *.spec.ts , (^|/)tests/
```

`services/api` を迎えると **3 箇所**が検出される（実測済み・`spec.md` R6.4 の表）。3 件とも
docstring 内の書式例であり、移植元の guard は代入形のみを見るため元 repo では green である。

| 案 | 効果 | 副作用 |
|---|---|---|
| (a) carve-out 追加 | 即時 | carve-out が 3 → 5 に増え、ゲートの射程が静かに縮む |
| (b) docstring 改稿 | 即時 | 移植元の文書品質を下げる。上流との diff が増える |
| **(c) 代入形検出へ精密化** | ゲートが**より正確**になる | 実装コスト。両ガード併存によるドリフト |

(c) を既定とする理由は統合計画 §4.4 と同型 — **より厳しい／より正確な側が家の標準になる**方向。
ただし (c) はハブの shell grep と `services/api` の pytest guard を併存させるため、
carve-out リストの**ドリフト検出テスト**を同時に入れる（R6.5）。これが無いと 2 つのガードが
別々の carve-out を持ち、片方だけが緩む事故が静かに起きる。

Phase 3 の教材コードでは **2 箇所**が検出され、そちらは**実際の代入**であるため (c) でも
検出は残る（R7.3）。これは正しい挙動であり、移設時に allowlist へ寄せる作業が必要という
シグナルである。

### 2.5 `services/api` の CI 形状

`python.yml` と**同型**にする。理由は同一（path-filtered job は多くの push で不在になり、
`needs` + `if: always()` の required check を壊す）。

```
.github/workflows/api.yml
  on: push/pull_request  paths: [ 'services/api/**', 'mise.toml', '.github/workflows/api.yml' ]
  permissions: contents: read          # 6/6 の既存規律を維持
  uses: すべて 40 桁 SHA 固定           # 28/28 の既存規律を維持（X-1）
  steps: mise-action → mise run api:check
  gate 集約（tests.yml）には含めない    # NFR-1 / R6.3
```

新規 workflow が増えるため、移植する `test_ci_workflows.py`（R6.6）の走査対象は 6 → 7 になる。
同テストの**非空アサート**（走査ファイル数 > 0）は移植時の必須追加項目（X-1）。

### 2.6 リテラル更新の同時性（R2.5）

`Chat.tsx:124` の `<h1>` を変えると `home.spec.ts:6` と `a11y.spec.ts:18` の
`getByRole("heading", { name: "vaz-ai-next" })` が同時に落ちる。`.githooks/pre-push` は
Playwright E2E を走らせるため、3 ファイルを別コミットに分けると push が赤になる。

→ **1 コミットに 6 ファイル**（`package.json` / `layout.tsx` / `Chat.tsx` / 2 spec / `README.md`）。

### 2.7 Task 7 — パターンカタログは移設しない（R7.1/R7.2）

R7.2 は「教材用の単純版を**ガイドの正本とする**」と述べるが、これは「物理的にこのハブへ
移設する」ことを要求していない。Task 6（`services/api`）との対比で判断した:

| 観点 | Task 6（`services/api`） | Task 7（パターンカタログ） |
|---|---|---|
| 移設元の性格 | 単体で動く**本番アプリケーション** | **書籍の実装コード**（`docs/part{1..5}/ch{01..14}.md` と 1 対 1 対応） |
| 移設先での役割 | ハブの一部として実際にデプロイ・運用される | 教材として「読む」対象。実行される想定はガイドの外 |
| 移設しない場合の損失 | ハブが本来提供すべき Python API レーンが欠ける | ほぼ無い — リンクで全く同じ内容に到達できる |
| 移設した場合の losses | なし（本番コードは単一の家を持つべき） | **書籍原稿（Phase 1 で link-only と決めた 14 章）から
  実装コードだけが引き剥がされる** — 解説と実装が別リポジトリに分裂し、読者体験が悪化する |

後者の「分裂」が決定的だった。R5.3 で書籍原稿 14 章を**リンク参照のみ**とした判断
（実体移設は「Task 7 の裁定に従う」と留保していた）と整合させるなら、**コードだけを先に
移設し、後から章が追いつく**という状態を作ってはならない。章ごと移設するなら
それは Phase 1 の判断のやり直しであり、Phase 3 の軽量な「取捨選択」の範囲を超える。

**結論**: `docs/guide/agentic-engineering.md` に 6 パターンそれぞれの正本（教材の単純版）と
比較版（sandbox の 3 FW 実装）を明示するリンク表を追加し、**どちらも物理的には移設しない**。
R7.3（model-ID 2 箇所の allowlist 対応）は「移設される時」の条件付き要件であり、
移設しない以上トリガしない — `lint:model-ids` は追加の carve-out なしで green のままである。

## 3. Phase 間の依存と独立性

```
R1 退避 ──→ R2 同一性移行 ──→ R3 正本設置 ──→ R4 憲章・継承 spec
                  │                                    │
                  │                                    ↓
                  │                              ADR-0003
                  ↓
            R9.1 参照検証（rename 直後に実行）
                                                       ↓
                                        R5 ガイド背骨（コード移動ゼロ）
                                                       ↓
                                        R6 services/api ──→ R8.3 ADR-0004
                                                       ↓        （TS/Python 語彙が同居した時点で起票）
                                        R7 patterns ──→ R8.5 I-H10 移植
                                                       ↓
                                        R9.4 旧 repo 整理（Phase 2 着地後のみ）
```

**NFR-1 の担保**: R1〜R5 はコード移動ゼロ。`mise run check` の構成に触れないため、
Phase 2 以降の未決定（統合計画 §8-3: 43,592 LOC を丸ごと移すか否か）を待たずに着地できる。
